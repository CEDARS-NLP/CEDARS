# Predictors, LLM client and NLP

Last verified: cef611321063 on 2026-10-05 (source + live read-only)

This area is the plumbing under evaluation and annotations: predictor configs (`/predictors`, LLM or PINES) used by the API-only bulk predictions; the shared LiteLLM client (`backend/app/llm/client.py`) that every LLM call goes through (evaluation classification, query suggestion, pattern generation, `LLMPredictor`); the spaCy + NegEx engine (`backend/app/nlp/engine.py`) and its `/nlp/*` API; and the legacy `/pipeline/events` API. Admins change things here and every role can read. Since 27320f5f removed the old Pipeline, Evaluation and Predictor pages, users reach only the LLM client (through project LLM settings) and the NLP engine (through evaluation search). Overall: predictor configs, `/nlp/*` and `/pipeline/events` are api-only; PINES is a stub, because its request and response shapes do not match the PINES service and no v2 deployment runs it; the LLM client is beta (stable pending live); and the NLP engine has query-parsing defects that also hit evaluation search.

Why the grades:
- **pred-\*, nlp-\* (API), pred-pipeline-events**: nothing in `frontend/src` calls them from a reachable page. The only callers of `/nlp/*` are in the orphaned `NlpQueriesSection.tsx`, and nothing calls `/predictors` or `/pipeline/events`. `JobDashboardPage` uses only `/pipeline/runs/*` and `/pipeline/queue` (see [jobs.md](jobs.md)).
- **pred-pines**: whatever PINES returns, v2 reads label 0 and score 1.0 (see Gotchas).
- **llm-\***: reachable through project LLM settings and every evaluation LLM call. The suites cover them, but nothing was driven live today: `llm calls` showed 0 calls, and Bedrock needs approval.
- **nlp-engine**: reachable through evaluation search, but AND, multi-word terms and parentheses do not work (see Gotchas).

## How to get to it (user POV)

1. No page manages predictor configs, NLP queries or EventConfigs. Use the API.
2. LLM client: an admin sets "LLM provider", model and API base on the project (create page or Overview settings; see [projects.md](projects.md)). Every evaluation sample run, query suggestion and full pipeline then goes through `llm/client.py`.
3. NLP engine: an admin types search queries in an evaluation session (see [evaluation-setup.md](evaluation-setup.md)). The session search runs `parse_query` and `process_note` on every note and keeps sentences that are targets and not negated (`evaluation/service.py:292-301`).

## Driving it with control-cedars

Preconditions: the baseline. The seeded project has 0 predictor configs, 0 NLP queries, 0 sentences and 0 EventConfigs (checked live 2026-10-05). Its LLM settings are `vllm` / `fake-clinical` / `http://fake-llm:8080`. Everything except the GETs changes data, so run it only in the mutation pass.

- **pred-crud**: `$CC api GET /projects/{project}/predictors --as viewer` → HTTP 200 `[]` (driven 2026-10-05). `$CC api GET /projects/{project}/predictors/00000000-0000-0000-0000-000000000000 --as viewer --expect 404` → `Predictor not found` (driven). Create: `$CC api POST /projects/{project}/predictors --as admin --body '{"name":"fake","predictor_type":"llm","config":{"provider":"vllm","model":"fake-clinical","api_base":"http://fake-llm:8080","api_key":"sk-test"}}' --save pred` → 201. Gating: the same POST `--as annotator --expect 403`.
- **pred-activate**: `$CC api POST /projects/{project}/predictors/<id>/activate --as admin` → `is_active: true`. A second config activated → the first returns `is_active: false`.
- **pred-test**: `$CC api POST /projects/{project}/predictors/<id>/test --as admin --body '{"text":"Acute DVT of the left leg."}'` → HTTP 200 `{"label":0,"score":0.15,"reasoning":"fake-llm: no positive term in 0 excerpts",...}`. The fake LLM only reads the evaluation excerpt format, so this path is always negative with the fake. `$CC llm calls --tail 1` → one call. With `"api_base":"http://nowhere:1"` → 422 `Cannot connect to vllm: ...`.
- **pred-llm**: covered by `pred-test`. A positive result needs a real model: SKIP, real Bedrock needs cost approval.
- **pred-pines**: SKIP. No PINES service runs in the parity stack, in `docker-compose.v2.yml` or in `infra/cedars-v2/`. Pointing `pines_api_url` at a dead host → `pred-test` returns 422 `PINES prediction failed: ...`.
- **llm-client-providers / llm-openai-compatible**: run any evaluation LLM step (see `evaluation-run.md`) → `$CC llm calls --json --tail 5` → each new call records `model: fake-clinical`. The fake answers only `*/chat/completions` (`.claude/skills/verify-cedars/stack/fake_llm.py:132-134`), so a logged call means the `openai/` + `/v1` path was taken.
- **llm-json-mode**: after any evaluation LLM step, `$CC llm calls --json --tail 5` → `response_format: {"type":"json_object"}` on classifier calls (vllm is native JSON mode). `$CC llm mode empty` (mutation pass only), then run an evaluation sample → patients fail with `Classification response has no 'event_detected' field`; none is silently negative. Restore with `$CC llm mode normal`.
- **llm-bedrock**: SKIP by default (cost). With user approval: `$CC bedrock probe --yes-cost`.
- **nlp-queries**: `$CC api GET /projects/{project}/nlp/queries --as viewer` → `[]` (driven). `$CC api GET /projects/{project}/nlp/queries/00000000-0000-0000-0000-000000000000 --as viewer --expect 404` → `Search query not found` (driven). Then `$CC api GET /projects/{project}/nlp/stats --as viewer` → `processed_notes: 103`, `target_sentences > 0`. Run it again → nothing new is processed.

## Gotchas

- **The query parser drops AND, phrases and parentheses.** These were reproduced in-process today, and they affect evaluation search and the full pipeline (`evaluation/service.py:292-297`, `worker.py:212-225`, `:336-338`):
  - AND is not enforced: any one positive condition makes a sentence a target (`engine.py:201-218`), so `troponin AND elevated` matches "Troponin was drawn.";
  - multi-word terms never match, because each term becomes one `LOWER` token pattern (`engine.py:157`). `pulmonary embolism` finds nothing;
  - parentheses are stripped only at the ends of the string and of each OR group (`engine.py:111`, `:118`). The docstring's own example, `(DVT OR embolus) AND !suspected` (`:99`), parses to the term `embolus)`, so "Large embolus seen." does not match;
  - `tests/test_nlp.py::TestQueryParser::test_parenthesized_groups` only asserts `len >= 1`.
- **Negation catches only cues that come first.** No deployment sets `CEDARS_SPACY_MODEL` (`config.py:51` defaults to `""`), so every stack uses `spacy.blank("en")` with a sentencizer (`engine.py:31-66`), and negation is the 5-token look-back. "DVT was ruled out." comes out as target and not negated. The cue list holds single words only (`engine.py:21-25`).
- **NLP run skips processed notes.** `_process_notes_into_sentences` handles only notes with no sentences (`nlp/service.py:234-246`). New or edited queries change nothing until `/reprocess`. All active queries are merged into one OR list (`:229-232`).
- **Reprocess destroys review work.** `clear_sentences` runs `DELETE FROM annotations WHERE project_id = :pid` (`nlp/service.py:403-406`). That deletes evaluation-pipeline annotations and reviewer decisions too, with no confirmation and no audit row. It runs synchronously inside the HTTP request (`nlp/router.py:151-160`).
- **`pred-crud` has a known security defect.** Details are tracked privately, not in this public repo.
- **Evaluation never uses a predictor config.** Sessions always classify with the project's LLM settings (`evaluation/service.py:530`, `:638`, `:700` → `classify_patient`). There is no predictor picker, so PINES or a predictor config cannot be evaluated through the UI. Only the API-only bulk predictions read `/predictors`.
- **PINES cannot work in v2.** `infra/cedars-v2/README.md:176` calls PINES "deferred/optional in v2", but CLAUDE.md's deferred list does not include it. The map grades `pred-pines` `stub`, not `deferred`, because the code ships and is reachable through the API.
  - `/predict` returns `{"prediction": ..., "model": ...}` (`PINES/pines.py:90`). The client reads `score` and `label` and defaults both, so it always gets label 0 and score 1.0 (`predictors/pines.py:35-40`).
  - The batch body `{"texts": [...]}` does not match the service's `list[Note]` (`PINES/pines.py:95`). That gives 422, and the client falls back to single calls (`pines.py:67-69`).
  - The default URL `http://localhost:8000` does not match the service port 8036 (`PINES/pines.py:110-113`).
  - `Settings.pines_api_url` (`config.py:39-40`) is never read.
  - No v2 compose file or Terraform defines a PINES service.
- **`LLMPredictor` still invents negatives.** A `{}` or partial reply defaults to `event_detected=False` and `confidence=0.5`, giving label 0 and score 0.5 (`predictors/llm.py:163-168`). An unparseable reply gives label 0 and score 0.0 (`:155-161`). cef61132 fixed this class of bug in the classifier (`pipeline/classifier.py:121-129`) but not here. `response_format` is never sent on this path.
- **`pred-test` has a known security defect.** Details are tracked privately, not in this public repo.
- **No provider allow-list in v2.** Any string up to 50 chars is accepted (`projects/schemas.py:9`). Unknown providers reach LiteLLM with a bare model name (`client.py:99`). CLAUDE.md's "Provider whitelist" describes v1.
- **The classifier truthiness is loose.** `bool(data.get("event_detected"))` treats the string `"false"` as True (`pipeline/classifier.py:131`).
- **Two job-status endpoints.** `/nlp/run` writes a `BackgroundJob` (`/nlp/job/status`). Reprocess writes a legacy `NlpJob` (`/nlp/job`, `nlp/service.py:286`). The orphaned UI read only `/nlp/job` (`NlpQueriesSection.tsx:40`).
- **The ARQ fallback hides a missing worker.** When `arq:queue:health-check` is absent, NLP and prediction jobs run in-process with `asyncio.create_task` in the web container (`nlp/service.py:114-153`, `annotations/prediction_service.py:196-232`). They die if the container restarts.
- **Synthetic EventConfigs.** Every evaluation commit adds a committed EventConfig, because `PipelineRun.event_config_id` is NOT NULL (`evaluation/service.py:1127-1156`). The legacy `/pipeline/events` list therefore grows with each commit, and the copied project `llm_api_key` is stored on it (`:1151`). `EventConfigResponse` does not return that key (`pipeline/schemas.py:36-50`).
- **The fake LLM only knows the evaluation prompts.** It parses `--- Excerpt from note ...` blocks (`.claude/skills/verify-cedars/stack/fake_llm.py:39-42`, `:65-66`). `LLMPredictor` prompts never match, so every `pred-test` and bulk prediction against the fake comes back negative with confidence 0.85, i.e. score 0.15 (`:80-86`).
