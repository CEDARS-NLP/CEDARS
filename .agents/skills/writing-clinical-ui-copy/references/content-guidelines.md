## Overview

Use these guidelines to help create consistent, useful, global language that supports the broader brand strategy. Although these guidelines assume a certain level of technical writing proficiency, they also address some common writing basics and points of style where content choices may vary.

These content guidelines are excerpted and adapted from standard industry style guides, including:

- MSK Brand Voice Summary
- MSK Marketing & Communication Style Guide
- Chicago Manual of Style
- Merriam-Webster's Collegiate Dictionary
- PRISM Readability Toolkit
- Microsoft Writing Style Guide
- Ethos Design System Editorial Guidelines (GE HealthCare)

## Key Takeaways

- Use consistent messaging (i.e., what we communicate) and voice (i.e., how we communicate) throughout the user interface (UI) of applications and websites.
- Choose language that can be translated easily and localized for an international audience.
- Use sentence case whenever possible, limiting use of title case for proper nouns and all capitals for acronyms.
- Ensure consistent meanings for abbreviations by relying on industry or standard definitions.
- Be concise, using simple, specific words that can be understood by all levels of readers and that mimic natural speech.
- Use active voice unless passive voice is necessary.
- Use gender-neutral language.

## Core Principles

- **Compassionate:** Messaging should be relatable and written in the way humans speak.
- **Inclusive:** Choose terms that can be easily translated and localized.
- **Concise:** Keep messages clear and free from unnecessary words.

## Readability

### Target Reading Level

Per MSK Patient & Community Education guidelines, target reading levels by content type:

| Content type | Target reading level |
|---|---|
| Patient-facing UI / instructional patient content | Grade 6 |
| Disease guides and condition overviews | Grade 6–8 |
| General web content | Grade 10–12 |
| Clinician-facing content | Higher level acceptable for clinical terms |

Nearly half of American adults read at or below an 8th-grade level, and research shows that even people with above-average reading skills prefer easy-to-read information. For clinician-facing UI, a higher reading level is acceptable for clinical terminology, but instructional and navigational text should still be as plain as possible.

### How to Self-Check Readability

- **Read your copy aloud.** If you stumble, the sentence is too complex. Rewrite it.
- **Count your sentence length.** Aim for an average of **15 words or fewer** per sentence in clinical UI. Vary sentence length for natural flow, but if any sentence exceeds 20 words, break it up.
- **Ask someone unfamiliar with the project to read it.** If they hesitate or ask a question, the copy needs revision.

## Best Practices

### Capitalization

Use sentence case capitalization.

Use sentence case — capitalizing only the first letter of the first word — for nearly all UI text, labels, buttons, links, section titles, and page headings.

- **Do:** Use sentence case for common nouns (e.g., "Create a new account").
- **Don't:** Only use title case for proper nouns (e.g., "Create A New Account").

Only use title case capitalization for proper nouns such as product names.

When using title case, capitalize each word, except:

- Articles (a, an, the)
- Conjunctions (for, and, nor, but, or, yet, so)
- Prepositions with four or fewer letters (in, on, with, from)

| Correct | Incorrect |
|---|---|
| In-basket | In-Basket |
| Date/time | Date/Time |
| Mismatch (yes/no) | Mismatch (Yes/No) |

Generic versions of proper nouns and product names are displayed in lowercase.

| Proper noun | Generic version |
|---|---|
| MyMSK | patient portal |
| Epic | electronic health record |
| InBasket | message inbox |

**Table headers and column labels** also use sentence case. This applies to data tables, lab result displays, medication lists, and schedule views.

| Correct | Incorrect |
|---|---|
| Appointment date | Appointment Date |
| Medication name | Medication Name |
| Last updated | Last Updated |

### Acronyms and Abbreviations

**Always define acronyms at first use.**

Write out the official title followed by the acronym in parentheses the first time it is referenced on a page in your application or website. You may use just the acronym after the first reference on the same page.

| Correct | Incorrect |
|---|---|
| Show the system status within the user interface (UI). | Show the system status within the UI. |
| The central processing unit (CPU) is a key component of any computer system. | The CPU is a key component of any computer system. |
| The World Health Organization (WHO) plays a crucial role in global health initiatives. | The WHO plays a crucial role in global health initiatives. |

**Use all caps for acronyms.**

All caps can be used for acronyms. Note that in rare instances some acronyms may include lowercase characters (such as mRNA).

| Correct | Incorrect |
|---|---|
| Show the system status within the UI. | Show the system status within the Ui. |
| The CPU is a key component of any computer system. | The cpu is a key component of any computer system. |
| The WHO plays a crucial role in global health initiatives. | The Who plays a crucial role in global health initiatives. |
| mRNA vaccines have saved millions of lives. | MRNA vaccines have saved millions of lives. |

**Use abbreviations and acronyms consistently.**

Use abbreviations consistently, leveraging standard definitions, and do not create your own. Pluralize abbreviations only when needed for clarity.

| Correct | Incorrect |
|---|---|
| Ensure all records are updated in the Electronic Health Record (EHR) system. | Ensure all records are updated in the Electronic Health Record (e-HR) system. |
| Review the MRIs before proceeding. | Review the MRI's before proceeding. |

**Use standard abbreviations with no definition.**

Use common abbreviations (such as e.g., i.e., etc., and vs.) with no additional explanation.

- Use "e.g." (followed by a comma) to mean "for example."
- Use "i.e." (followed by a comma) to mean "that is" or "in other words."
- Do not use "and" before the "etc." abbreviation, which means "and other similar things" or "and so on."
- Use "vs." (with the period at the end) to indicate a contrast, comparison, or competition between two entities or options.

> **Patient-facing exception:** In patient-facing UI text, avoid "e.g.," "i.e.," and "etc." Use plain language alternatives: "for example" or "such as" instead of "e.g."; "that is" or "in other words" instead of "i.e."; and list items explicitly rather than trailing off with "etc."

| Correct | Incorrect |
|---|---|
| We offer a variety of fruits in our store, including apples, bananas, oranges, etc. | We offer a variety of fruits in our store, including apples, bananas, oranges, and etc. |
| Prepare a summary of your project plan, i.e., provide an overview of the objectives. | Prepare a summary of your project plan, i.e. provide an overview of the objectives. |
| The debate between manual testing vs. automated testing continues. | The debate between manual testing vs automated testing continues. |
| Consider adding elements like fresh herbs, e.g., basil or cilantro, to enhance flavor. | Consider adding elements like fresh herbs, e.g. basil or cilantro, to enhance flavor. |

### Tone and Perspective

**Avoid superlatives.**

Although superlatives may be acceptable in some cultures, other cultures might find them unacceptable as a method of promoting features, so avoid them. Regulatory issues concerning unfounded product claims also may arise in clinical settings.

| Correct | Incorrect |
|---|---|
| We are innovating to improve efficiency. | We have the most efficient products in the industry. |

**Use a first- or second-person perspective.**

Address users directly using a suitable tone from the correct point of view (such as second person perspective for direct communication). Don't use unclear or impersonal language.

- **Do:** Address users directly. (e.g., "You have successfully saved your changes.")
- **Don't:** Don't use impersonal language. (e.g., "Changes have been successfully saved.")

**Contractions are acceptable in conversational UI text.**

Common contractions help maintain a conversational, human tone and are appropriate in most UI text, including tooltips, helper text, empty states, and onboarding flows. Per the MSK Patient & Community Education team and the US Federal Plain Language Guidelines, use the following categories:

- **Do use contractions** in instructional text, helper text, and messages where a conversational tone is appropriate.
- **Avoid contractions** in formal or high-stakes contexts such as legal disclaimers, consent language, or destructive action confirmations where precision and gravity matter.
- **Avoid "not" contractions in important instructions** (e.g., use "Do not eat after midnight," not "Don't eat after midnight"). They are acceptable elsewhere.

| OK to use | Use with caution | Do not use |
|---|---|---|
| he's, I'll, I'm | aren't, can't, didn't | couldn't, hadn't, hasn't |
| it's, let's, she's | doesn't, don't, he'll | haven't, he'd, I'd |
| that's, there's, they'll | I've, isn't, she'll | mightn't, mustn't, shan't |
| they're, we're, what's | they've, wasn't, we've | she'd, shouldn't, they'd |
| where's, who's, you're | who've, wouldn't, you'll | we'd, weren't, what'll |
| | you've | who'd, who'll, who're |
| | | won't, would've, you'd |

**Note:** When the distinction between "do not" and "don't" affects clarity or emphasis — particularly in warnings or destructive actions — use the uncontracted form for added weight.

## Writing Checklist

### 1. Cut any word that does not serve a purpose

Remove filler words and redundancies.

| Correct | Incorrect |
|---|---|
| Add items to the list. | You can add items to your list. |
| Add medication. | Add a new medication. |
| Low battery. Plug in your device. | Warning! Your battery is low. Plug in your device. |
| Create your account. | Welcome to the Portal: Create your account in minutes! |

### 2. Use clear, self-explanatory language

- Ensure headings describe the material that follows.
- Use button labels to describe the action.
- Ensure that hyperlinks are descriptive and easily understood on their own to support accessibility.
- Use headings as "road signs" to help users navigate screens, settings, and multi-step flows. A heading should tell the user what they will find in that section without requiring them to read the content below it.
- Put the most important keyword or concept at the **beginning** of headings, labels, and table entries so they are easy to spot when scanning.
- Use **parallel structure** for headings at the same level, list items in the same list, and labels in the same group. If one item starts with a verb, they should all start with a verb. If one is a noun phrase, they should all be noun phrases.

| Correct (parallel) | Incorrect (mixed) |
|---|---|
| View appointments · Schedule appointment · Cancel appointment | View appointments · Scheduling · Cancel |
| Enter your name · Select your department · Confirm your details | Enter your name · Department selection · Confirm your details |

| Correct | Incorrect |
|---|---|
| Learn more about side effects. | Learn more. |
| Submit. | Done. |
| Create account. | Click here to create account. |

### 3. Use words your users use every day in a consistent way

- Avoid using terms that users must learn to understand.
- Avoid using terms that might be easily confused with other terms.
- Ensure terms are used consistently across the application ecosystem.
- For patient-facing text, replace medical and technical jargon with plain language equivalents. Consult `references/clinical-plain-language.md` for common substitutions.
- When a clinical term cannot be avoided (e.g., it appears in a lab result or diagnosis), provide a brief plain language explanation on first appearance in the UI flow.

MSK-recommended plain language substitutions:

| Avoid | Use instead |
|---|---|
| novel | new |
| physician | doctor |
| patient | you / people with [condition] |
| cohort (patient-facing) | group |
| hospital setting (patient-facing) | at the hospital |
| and/or | or both (use the form: a, b, or both) |
| minority (for patients) | rephrase with specific group or context |

**Words and phrases to avoid in patient-facing UI:**
- "cohort" — use "group" instead
- "hospital setting" — use "at the hospital" or "at MSK"
- "minority" to describe patient populations — rephrase with specifics
- "cancer patient" — prefer "people with cancer" or address as "you"
- "your cancer" — prefer "the cancer" or rephrase
- "teleconsult," "tele-oncology," "televisit" — use "telemedicine" or "telehealth"

| Correct | Incorrect |
|---|---|
| The medicine is available for purchase at the local pharmacy. | The medicine is available over the counter. |

### 4. Use natural, conversational language that speaks directly to users

- Use short, direct sentences with one clear thought and that contain 10–20 words or less.
- In clinical interfaces, aim for an average of **15 words or fewer** per sentence. Vary sentence length for natural flow.
- Avoid compound sentences.
- Use simple, specific words that can be understood by all levels of readers and that mimic natural speech.
- Avoid technical jargon.

| Correct | Incorrect |
|---|---|
| To continue, complete all required fields. | Ensure that you have completed all of the items that have been designated. |
| You do not have permission to access the [item]. | The [item] for which an access attempt has been initiated does not contain. |
| Use active voice unless passive voice is necessary. | Use active voice except in certain cases where passive voice is necessary. |

### 5. Write in active voice

In active voice, the subject performs the action. In passive voice, the subject receives the action.

| Correct | Incorrect |
|---|---|
| Select your top two priorities. | Your top two priorities can be selected. |
| Help our organization raise funds. | Our organization needs help raising funds. |
| Use this as an example. | This is an example of what we can do. |

### 6. State things positively

- Tell users what they can do rather than what they can't do.
- Tell the user how to fix an error instead of just pointing it out.
- Use negative words (such as "not," "cannot," and "never") sparingly.

| Correct | Incorrect |
|---|---|
| Enter a valid email address. | You cannot proceed with an invalid email address. |
| The file size must be under 5 MB. | The file you uploaded is too large. |
| System maintenance is scheduled for Sunday. | The system will not be available on Sunday. |

### 7. Lead with the most important information

- In error messages, state what went wrong before explaining how to fix it.
- In notifications, state the outcome or change before providing detail.
- In instructional text, state the user's goal or benefit before listing steps.
- In multi-paragraph UI text (help content, onboarding), put the most critical information in the first sentence — users often read only the beginning.

| Correct | Incorrect |
|---|---|
| Your appointment has been canceled. To reschedule, select a new date. | We wanted to let you know that the appointment you had previously scheduled has been canceled by the system. You may reschedule at your convenience. |
| Your test results are ready. View them in the results tab. | A notification has been generated because there is an update to your account. Your test results are now available. |

### 8. One main idea per paragraph or text block

- Each paragraph, list item, or instructional step should contain exactly one idea.
- If a sentence covers two topics, split it into two sentences.
- In bulleted lists, keep each item to a single point — do not embed multiple instructions in one bullet.
- This reduces cognitive load, especially in clinical contexts where users may be stressed, distracted, or processing difficult information.
- Keep paragraphs short: **three to seven lines** is the right length. A single-line paragraph is acceptable when it improves scannability.

| Correct | Incorrect |
|---|---|
| Bring your insurance card. *(separate line)* Arrive 15 minutes early. | Bring your insurance card and arrive 15 minutes early so we can verify your coverage and get you checked in. |

## Formatting

### Dates and Times

Write out the month, use a space, and write the one- or two-digit day, followed by a comma and the four-digit year.

- **Do:** Spell out the month (e.g., October 31, 2021). For UI constraints, use the three-letter abbreviation for the month (e.g., Oct 31, 2021).
- **Don't:** Do not use all numbers for dates (e.g., 10/31/2021), as date formatting conventions vary globally.

When formatting times, use a 12-hour clock followed by a space and "am" or "pm" in lowercase.

- **Do:** Include minutes for clarity, even if it is on the hour (e.g., 9:00 am).
- **Don't:** Do not use a 24-hour format or uppercase AM/PM.

| Correct | Incorrect |
|---|---|
| Oct 31, 2021 | 10/31/2021 |
| 9:00 am | 09:00 AM |
| 2:30 pm | 14:30 |

### Numbers

Use numerals for numbers in UI copy.

- **Exceptions:** Always use numerals for measurements, percentages, ages, and when referring to specific UI elements or sequential steps.
- **Patient-facing content:** Continue to prioritize numerals in patient-facing UI text because figures are easier to scan and process, especially for patients reviewing clinical data.

| Correct | Incorrect |
|---|---|
| 3 patients are waiting. | Three patients are waiting. |
| There are 12 items in the queue. | There are twelve items in the queue. |
| The dose is 5 mg. | The dose is five mg. |
| Set the threshold to 20%. | Set the threshold to twenty percent. |

### Text Alignment

- Use **left-aligned text** for all UI content. Left alignment creates a consistent starting point for each line, making text easier to scan.
- **Do not center-align** body text, labels, or instructional content. Centered text is harder to read, especially on data-dense clinical screens.
- Centered text is acceptable only for single-line elements in specific design contexts (e.g., a hero message on a welcome screen), and only when approved by the design team.

## Punctuation

### Periods

Do not use periods at the end of isolated phrases, list items (unless they are full, independent sentences), UI labels, buttons, tooltips, or hover text.

| Correct | Incorrect |
|---|---|
| Save changes | Save changes. |
| Patient ID | Patient ID. |

### Commas

Use the serial (Oxford) comma before the coordinating conjunction (and, or) in a list of three or more items to prevent ambiguity.

| Correct | Incorrect |
|---|---|
| Review the patient's history, lab results, and imaging. | Review the patient's history, lab results and imaging. |
| Send the report to the doctor, nurse, or administrator. | Send the report to the doctor, nurse or administrator. |

### Exclamation Points

Avoid using exclamation points. In a clinical or professional software context, they can come across as alarming, unprofessional, or like shouting.

| Correct | Incorrect |
|---|---|
| Your changes have been saved. | Your changes have been saved! |
| Warning: low battery. | Warning: low battery! |

### Hyphens and Dashes

Use hyphens and dashes correctly to maintain professionalism and clarity.

- **Hyphen (-):** Use to join words or parts of words (e.g., follow-up appointment).
- **En dash (–):** Use to indicate a range of numbers or dates (e.g., 2021–2022).
- **Em dash (—):** Use with a space on either side to indicate a break in thought (e.g., The results — though delayed — were completely accurate.).

### Quotation Marks

Use quotation marks for direct quotes or when referring to a specific title, input, or UI element. Place periods and commas inside the closing quotation marks.

| Correct | Incorrect |
|---|---|
| The file status is "Pending." | The file status is "Pending". |
| Select "Save" to continue. | Select "Save", to continue. |

### Ampersands and Special Characters

- Do not use ampersands (&) or plus signs (+) in headings, labels, or button text. Spell out "and" instead.
- Ampersands are acceptable only when they appear in an established product name or brand (e.g., "AT&T").

| Correct | Incorrect |
|---|---|
| Billing and insurance | Billing & insurance |
| Appointments and referrals | Appointments & referrals |

## Glossary

Use this glossary to ensure consistency when selecting terms for your UI or documentation.

| Term | Usage | Do / Don't |
|---|---|---|
| Select | Use when picking from options, selecting a button, or choosing a checkbox. | **Do:** Select "Save." **Don't:** Click "Save," Tap "Save." |
| Sign in | Use for entering an account or system. | **Do:** Sign in to your account. **Don't:** Log in, Log on. |
| Drop-down | Use as an adjective, not a noun. Always hyphenate. | **Do:** Select an option from the drop-down menu. **Don't:** Select an option from the dropdown. |
| Set up / Setup | Use "set up" as a verb. Use "setup" as a noun. | **Do:** Set up the device. / Check the setup. **Don't:** Setup the device. |
| Checkbox | Always write as one single word. | **Do:** Select the checkbox. **Don't:** Check box, Check-box. |
| Email | Write as one word, uncapitalized (unless beginning a sentence). | **Do:** Send an email. **Don't:** Send an e-mail, Send an Email. |
| Please | Avoid using "please" in instructional UI text; it adds unnecessary words. Reserve it for situations where the user is inconvenienced. | **Do:** Wait while the system updates. **Don't:** Please wait while the system updates. |
| Toggle | Use to describe a switch component, not the action of turning it on or off. | **Do:** Turn on notifications. **Don't:** Toggle notifications on. |
| Wi-Fi | Capitalize the W and F, and include a hyphen. | **Do:** Connect to Wi-Fi. **Don't:** Connect to wifi, Connect to Wi-fi. |
